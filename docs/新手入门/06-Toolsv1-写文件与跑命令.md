# 06. Tools v1：写文件 + 跑命令（进入 coding agent）

到这一步，你的 Agent 才算真正“能干活”。

因为从这里开始，它不只是看代码、解释代码，而是能：
- 改代码
- 跑测试
- 根据结果继续修

也就是你想要的那句：**形成闭环**。

---

## 本章目标（验收标准）

完成下面这条，就算通过：

- “加一行日志 + 运行单测”能一次跑通

如果一次跑不通也没关系，关键是：
- 它能把失败信息读懂
- 它知道下一步该改哪里
- 它能把改动和验证串起来

---

## Tools v1 要补齐的两类能力

### 1) 写入工具：write / edit / patch（至少两种路径）

为什么建议至少两种：
- `write` 很直接，但容易误覆盖
- `edit` 更适合小范围改动
- `patch/diff` 最适合“先看差异再应用”，也更适合审计

最稳的组合通常是：
- v1 先做 `write + edit`
- 再逐步引入 `patch`（配合 diff 展示）

### 2) 命令工具：bash

bash 是 coding agent 的核心工具之一。

它让 Agent 能做三件非常实际的事：
- 跑测试
- 跑格式化/静态检查
- 快速探索项目（列目录、搜索、查看文件）

但也因为它太强，所以风险也最大。

---

## 入门版安全策略：简单，但必须有

本章不追求做出完整权限系统，但你至少要做到“别让它随便乱跑”。

下面是一个够用的入门策略（你可以按顺序实现）：

### 规则 1：默认 ask

只要是这两类动作，默认都要 ask：
- 写文件
- 运行命令

这一步的价值很直接：你至少能看一眼它要干什么。

### 规则 2：限制工作目录（workspace）

入门阶段最容易做、收益也很大的限制是：
- 命令只能在 workspace 内执行
- 写文件只能写 workspace 内

你会立刻少掉一大类“误操作”。

### 规则 3：危险命令先提示

你不需要把黑名单写得多完美，但至少要拦住明显危险项：
- 删除（rm / del / rmdir）
- 覆盖（> 重定向、覆盖写）
- 外部目录（..、绝对路径、驱动器根目录）

更重要的是：给出理由，让用户理解你为什么阻止它。

## 本章验收脚本（直接复制）

这里给你一条很稳的验收路径，能把“写文件 + 跑命令 + 观察结果”串起来。

### Step 1：让它先提出方案

```text
请在不修改代码的前提下，提出一个最小改动：在启动流程里加一行日志。
然后给出验证方式（怎么跑测试/怎么运行）。
```

### Step 2：确认后执行

```text
可以开始改动，但写文件或运行命令之前都要先问我确认。
每次执行后用 2 句话总结结果。
```

### Step 3：让它跑一次测试

```text
现在运行单测。若失败，请根据失败信息给出下一步修复，并再次跑测试。
```

你要观察的不是它一次就成功，而是它有没有把闭环跑起来：
- 改动 → 测试 → 失败 → 修 → 再测 → 收束

---

## 一点经验：为什么很多工具系统会“看起来能用，但很不稳”

常见原因是两类：

1) 写入太粗暴
- 只会整段覆盖写
- 没 diff、没定位、没最小修改

2) bash 没护栏
- 能跑，但你不敢让它跑

所以 Tools v1 的关键不是“加工具”，而是“把可控性带进来”。
