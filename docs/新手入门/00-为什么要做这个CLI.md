# 00. 为什么要做这个 CLI（先建立正确目标）

如果你把 Mini Kimi 当成“聊天机器人”，你会很快失望。

这套教程真正想带你做的是：一个能在终端里完成任务的**工程搭档（CLI Agent）**。

换句话说，我们追求的不是“会说话”，而是“能闭环、可控、可复用”。

---

## 我们真正想要的能力（不是口号，是验收标准）

下面这 5 点，就是你之后每一章都要反复对齐的“北极星”。

### 1) 在终端里完成完整任务

不是“回答问题”，而是**从目标到结果**：
- 修 bug
- 加功能
- 跑测试
- 改文件
- 总结与复盘

这要求 Agent 不只是生成文本，而是能调用工具、观察结果、继续推进。

### 2) 对仓库有真实理解（Repo Awareness）

我们不接受“模型脑补”。

想回答“入口在哪”“测试怎么跑”，必须基于真实仓库探索能力，比如 read / grep / list / glob / bash / edit / write / patch 这类工具组合。主流 CLI Agent 的工具体系基本都围绕这些动作展开。citeturn1search3

### 3) 有稳定闭环（Loop，而不是一次性回答）

真正可靠的 Agent，一定是循环系统：

```text
目标 → 计划 → 行动（工具）→ 观察（结果）→ 调整 → 完成
```

没有 loop 的系统，本质上只是“会写字的壳”。

### 4) 行为可控、可审计（安全是功能，不是附加项）

当 Agent 具有 bash / 写文件能力时，风险就已经进场了。

工程级 CLI Agent 的共识做法是：
- 用权限系统把行为分成 allow / ask / deny
- 支持模式匹配或通配规则
- 对高风险动作默认 ask

这不是理论，而是行业成熟产品的明确设计方向。citeturn1search0turn1search1

### 5) 能沉淀套路（Skills / Rules / Hooks / Plugins / MCP）

一次性“表现好”不难，难的是“下一次也好”。

成熟 CLI Agent 的共同演进方向是：
- 把经验沉淀成 skills
- 把团队约束固化为 rules / instructions
- 把“每次都要做的事”自动化为 hooks

尤其是 hooks，它的价值在于把“建议”变成“必然发生的动作”（例如每次写代码后自动格式化/校验）。citeturn0search2turn0search1

## 为什么说这不是拍脑袋（行业共识在这里）

你会发现，我们的目标拆解和主流 CLI Agent 的工程结构高度一致：

### 权限系统：allow / ask / deny 已经是事实标准

OpenCode 的权限模型就直接把动作分成 allow / ask / deny，并支持按工具和输入模式细分规则。换句话说，“可控性”不是附加功能，而是一级功能。citeturn1search0turn1search1

### hooks：把“应该做”变成“一定做”

Claude Code 的 hooks 官方文档强调：hooks 提供**确定性控制**，让某些动作总会发生，而不是依赖模型“自觉”。这正是工程化系统的关键差别。citeturn0search2turn0search1

### 工具优先：不是更会说，而是更会做

OpenCode 的工具文档也明确强调：工具让 LLM 能够在代码库中执行动作；而工具行为的边界与安全性，依赖权限系统来约束。这和我们教程的路线完全对齐。citeturn1search3turn1search0

## 0.2 现在市场上的 CLI Agent 到底在比什么（抽象成共识能力）

如果你把各种 CLI Agent 的实现细节去掉，最后留下的差异通常不是“模型是谁”，而是这些“工程能力是否完整”：

### 共识能力清单（之后我们会逐章落地）

1. 工具是第一性原理
- read / grep / list / glob / bash / edit / write / patch
- 重点不在工具多，而在工具边界清晰、结果结构稳定citeturn1search3turn1search0

2. 权限是安全底线
- allow / ask / deny
- 支持通配/模式匹配
- 高风险动作默认 askciteturn1search0turn1search1

3. Agent 是“角色配置”，不是单一人格
- 不同 agent 可以有不同权限与行为范围
- 工程上常见做法是给 plan/build 不同的能力边界citeturn1search5turn1search0

4. rules / instructions 是工程约束的入口
- 把“团队规范”变成系统输入，而不是靠人提醒
- 这也是从 demo 走向团队可用的分水岭citeturn1search7turn1search0

5. hooks / 自动化护栏是稳定性的放大器
- hooks 的价值是“确定性执行”
- 这能显著降低模型偶发性行为带来的波动citeturn0search2turn0search1

## 这一章的验收标准（非常具体）

读完这一章，你应该能做到两件事：

1. 用一句话讲清楚目标
- Mini Kimi 不是聊天壳，而是：LLM + 工具 + 循环 + 权限/护栏 + 经验沉淀。

2. 用一张简单流程图讲清楚闭环

```text
目标 → 计划 → 工具 → 观察 → 调整 → 完成
```

只要你把这两件事讲清楚，后面的章节就不会走偏。
